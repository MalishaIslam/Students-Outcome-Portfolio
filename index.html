The data, in plain English

Both projects use the Open University Learning Analytics Dataset (OULAD). The Open University is a UK distance-learning university. It published anonymised records of real students: who they were in broad terms, which courses they took, every assignment score, and how each course ended for them. No names or personal details are included.

28,785students
32,593course enrollments
22course runs
173,912assessment scores
Course run, e.g. BBB 2013J
One course (BBB) taught in one term. “J” runs start in October and “B” runs start in February.
Enrollment
One student taking one course run. A student who took two courses counts as two enrollments.
TMA, CMA, Exam
The three kinds of assessment: tutor-marked assignments, computer-marked quizzes, and final exams.

At-risk report

An early warning you can tune

Choose a day in the course and a rule (missed deadlines or a low average). The report lists who matches, then checks how those students actually finished.

Does the early warning work?

Because the dataset already knows how each course ended, the rule can be tested. Checking on day 60, flagging anyone who had missed at least one deadline or was averaging under 40:

Flagged on day 60 · 4,904 students81.3%

went on to fail or withdraw.

Not flagged · 21,457 students32.6%

went on to fail or withdraw.

A simple rule, two months in, picks out a group roughly two and a half times more likely to fail or withdraw. That is time for staff to reach out.

How it works

The website never touches the data tables directly. Every action goes through a small set of approved database routines (stored procedures), like a bank teller who can only process set forms.

Stored procedures

The only door into the data. Each one does one job.

SQL Server

Database

Students, enrollments, assessments, scores, audit log.

↳Getting the data in: the raw CSV files are loaded into a holding area first, then cleaned, converted, de-duplicated and moved into the real tables in a single all-or-nothing step, with a row count check so nothing goes missing.

Built to be safe

The records are anonymised, but the app treats them as if they were real.

Least access

The app's database account can only run the approved routines. It cannot read or change tables on its own.

No SQL injection

Typed values only, never pasted-together SQL. Sorting uses a fixed allow-list.

Sign-in everywhere

Every page and API needs a login. Repeated guessing is slowed to 5 tries a minute.

No overwriting

A version stamp on each record stops two people silently overwriting each other.

Checked twice

Input is validated in the app and again in the database.

Secrets kept out

Passwords live outside the code, and errors never show internal details to users.

Tested on every change

For developers: run it yourself

Needs Docker Desktop. The first start builds the database and imports the data (a minute or two).

# download the dataset (about 45 MB) into ./data
bash scripts/get-data.sh
cp .env.example .env            # then set the four values
docker compose up --build
# open http://localhost:5080 and sign in

Project 2 · Analytics

Student Outcomes Dashboard

The analytics companion to the web app. Where the app helps staff act on one student at a time, this Power BI report steps back and asks what patterns run through all 32,593 enrollments.

Power BI DesktopPower QueryDAX

The two report pages

Buttons move between the pages. Clicking any bar or segment filters the other charts on the same page.

How it was built

  1. Prepare

    Loaded the student file in Power Query and set the right data type for every column.

  2. Measure

    Wrote DAX measures for enrollments and the pass, withdrawal and distinction rates.

  3. Visualise

    Cards, donut, stacked bar, column, line and treemap charts with clear titles.

  4. Connect

    Added page buttons and cross-filtering so readers can explore.

See the DAX measures 
Total Enrollments = COUNTROWS(studentInfo)
Pass Rate         = DIVIDE(CALCULATE([Total Students], studentInfo[final_result] IN {"Pass","Distinction"}), [Total Students])
Withdrawal Rate   = DIVIDE(CALCULATE([Total Students], studentInfo[final_result] = "Withdrawn"), [Total Students])
Distinction Rate  = DIVIDE(CALCULATE([Total Students], studentInfo[final_result] = "Distinction"), [Total Students])

Pass Rate counts both Pass and Distinction as a successful finish.

What the data says

Four findings

The main takeaways from both projects, with the numbers behind them.

Overall

Fewer than half of enrollments end in a pass.

47.2% pass (including 9.3% with distinction). Almost a third withdraw before the course ends.

Pass + distinction47.2% Withdrew31.2% Failed21.6%

All 32,593 enrollments.

Prior education

Background matters a lot.

Students who already hold a postgraduate qualification pass about twice as often as those with no formal qualifications.

Postgraduate~65% No formal quals~30%

Pass rate by highest education level, Power BI report.

Start term

October starts do better than February starts.

In both 2013 and 2014, course runs starting in October (“J”) had higher pass rates than those starting in February (“B”). Course BBB shows it clearly:

BBB 2013 Feb45.4% BBB 2013 Oct47.9% BBB 2014 Feb45.1% BBB 2014 Oct50.3%

Pass rates from the web app dashboard.

Courses

Some courses lose far more students.

BBB and FFF are the largest courses. CCC stands out for withdrawals: well above the 31.2% average in both of its runs.

CCC 2014 Feb46.4% CCC 2014 Oct43.1% All courses31.2%

Withdrawal rate, from the web app dashboard (898 of 1,936 and 1,077 of 2,498).
